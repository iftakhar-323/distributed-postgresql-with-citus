# Lab 48: Query Plan Analysis and Benchmarking

In this lab, you will peek under the hood to see how Citus executes distributed queries. You will use the PostgreSQL `EXPLAIN` command to analyze execution plans for both single-tenant (single-shard) and cross-tenant (multi-shard) queries. Finally, you will perform a benchmarking test to measure the performance and throughput of inserting multi-tenant data into distributed tables.

## Concept

| Term | Definition |
|---|---|
| **Query Plan** | A sequence of steps generated by the database query optimizer to execute a specific SQL statement. |
| **EXPLAIN** | A PostgreSQL command that displays the execution plan that the planner generates for a supplied statement without running it. |
| **Single-Shard (Router) Query** | A query that provides a specific value for the distribution column (e.g., `tenant_id = 1`), allowing Citus to route it directly to exactly one worker shard. |
| **Multi-Shard (Adaptive) Query** | A query that spans multiple tenants or lacks a distribution filter, forcing Citus to fan out (scatter) the query across all worker shards and aggregate (gather) results. |

Understanding how Citus plans queries is critical for building high-performance, horizontally scalable multi-tenant applications.

### Create Database Schema (`database.py`)

In **Terminal 1**, create `database.py`:

```bash
cat << 'EOF' > database.py
from flask_sqlalchemy import SQLAlchemy
from sqlalchemy import text

db = SQLAlchemy()

class Tenant(db.Model):
    __tablename__ = 'tenants'
    id = db.Column(db.Integer, primary_key=True, autoincrement=True)
    name = db.Column(db.String(100), nullable=False)

class Product(db.Model):
    __tablename__ = 'products'
    id = db.Column(db.Integer, primary_key=True, autoincrement=True)
    name = db.Column(db.String(100), nullable=False)
    price = db.Column(db.Float, nullable=False)

class Order(db.Model):
    __tablename__ = 'orders'
    id = db.Column(db.Integer, primary_key=True, autoincrement=True)
    tenant_id = db.Column(db.Integer, primary_key=True)
    product_id = db.Column(db.Integer, nullable=False)
    quantity = db.Column(db.Integer, nullable=False)

def setup_database(app):
    with app.app_context():
        db.create_all()
        try:
            db.session.execute(text("SELECT create_distributed_table('tenants', 'id');"))
            db.session.execute(text("SELECT create_distributed_table('orders', 'tenant_id');"))
            db.session.execute(text("SELECT create_reference_table('products');"))
            db.session.commit()
        except Exception:
            db.session.rollback()
            pass
EOF
```

### Create Flask API (`app.py`)

In **Terminal 1**, create `app.py`:

```bash
cat << 'EOF' > app.py
import os
from flask import Flask, request, jsonify
from database import db, Tenant, Product, Order, setup_database

app = Flask(__name__)

COORDINATOR_IP = os.environ.get("COORDINATOR_IP", "127.0.0.1")
app.config['SQLALCHEMY_DATABASE_URI'] = f'postgresql://citus:citus_password@{COORDINATOR_IP}:5432/citus'
app.config['SQLALCHEMY_TRACK_MODIFICATIONS'] = False

db.init_app(app)
setup_database(app)

@app.route('/orders', methods=['POST'])
def create_order():
    data = request.get_json()
    new_order = Order(
        tenant_id=data['tenant_id'],
        product_id=data['product_id'],
        quantity=data['quantity']
    )
    db.session.add(new_order)
    db.session.commit()
    return jsonify({"message": "Order created", "order_id": new_order.id}), 201

@app.route('/orders/<int:tenant_id>', methods=['GET'])
def get_orders(tenant_id):
    orders = Order.query.filter_by(tenant_id=tenant_id).all()
    result = [{"id": o.id, "tenant_id": o.tenant_id, "product_id": o.product_id, "quantity": o.quantity} for o in orders]
    return jsonify(result), 200

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
EOF
```

## Step 2: Analyze a Single-Shard Query Plan

Open **Terminal 2**. Connect to the Citus coordinator container running on EC2 instance `controller-0`:

```bash
ssh -t controller-0 "sudo docker exec -it citus_coordinator psql -U citus -d citus"
```

Once connected to the `citus=#` prompt, execute an `EXPLAIN` query filtering by `tenant_id`:

```sql
EXPLAIN SELECT * FROM orders WHERE tenant_id = 1;
```

**Expected Output:**
```text
                                  QUERY PLAN                                  
------------------------------------------------------------------------------
 Custom Scan (Citus Router)  (cost=0.00..0.00 rows=0 width=0)
   Task Count: 1
   Tasks Shown: All
   ->  Task
         Node: worker-1:5432
         ->  Seq Scan on orders_102008 orders  (cost=0.00..24.50 rows=5 width=16)
               Filter: (tenant_id = 1)
(6 rows)
```

**Query Plan Breakdown:**
- **`Custom Scan (Citus Router)`**: Citus identified this as a point lookup on the distribution column (`tenant_id = 1`). It uses the fast "router" execution engine.
- **`Task Count: 1`**: Exactly one shard on one worker node needs to be contacted. There is zero cluster-wide coordination overhead.
- **`Node: worker-1:5432`**: Citus pinpointed the target shard (`orders_102008`) directly on worker node 1.

## Step 3: Analyze a Multi-Shard Query Plan

Now, run a query that does *not* filter by `tenant_id`:

```sql
EXPLAIN SELECT * FROM orders;
```

**Expected Output:**
```text
                                  QUERY PLAN                                  
------------------------------------------------------------------------------
 Custom Scan (Citus Adaptive)  (cost=0.00..0.00 rows=100000 width=16)
   Task Count: 32
   Tasks Shown: One of 32
   ->  Task
         Node: worker-1:5432
         ->  Seq Scan on orders_102008 orders  (cost=0.00..22.70 rows=1270 width=16)
(6 rows)
```

**Query Plan Breakdown:**
- **`Custom Scan (Citus Adaptive)`**: Because no partition key was specified, Citus must employ the adaptive executor to fan out queries in parallel.
- **`Task Count: 32`**: The query is dispatched to all 32 shards in the cluster simultaneously. The coordinator then collects and stitches together the results before returning them to the client.

## Step 5: Benchmark Multi-Tenant Inserts

In **Terminal 2**, navigate into the project directory and create a sample JSON payload:

```bash
cd ~/project/flask-citus-app
cat << 'EOF' > post_data.json
{"tenant_id": 1, "product_id": 1, "quantity": 1}

```

Run the benchmark against your Flask API (running on port 5000), issuing **1,000 requests** with a concurrency of **10 concurrent workers**:

```bash
ab -n 1000 -c 10 -T 'application/json' -p post_data.json http://localhost:5000/orders
```

**Expected Output Analysis:**
```text
Concurrency Level:      10
Time taken for tests:   1.842 seconds
Complete requests:      1000
Failed requests:        0
Total transferred:      173000 bytes
Total body sent:        197000 bytes
HTML transferred:       37000 bytes
Requests per second:    542.89 [#/sec] (mean)
Time per request:       18.420 [ms] (mean)
Time per request:       1.842 [ms] (mean, across all concurrent requests)
Transfer rate:          91.71 [Kbytes/sec] received
```

Key performance metrics to observe:
- **`Requests per second`**: The throughput achieved by the Citus cluster handling concurrent writes.
- **`Time per request`**: The round-trip latency experienced by clients when inserting data into distributed tables.
- **`Failed requests: 0`**: Verifies that Citus and Flask handle concurrent distributed transactions without deadlock or connection drops.
