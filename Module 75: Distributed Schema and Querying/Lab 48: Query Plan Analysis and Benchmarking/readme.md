# Lab 48: Query Plan Analysis and Benchmarking

In this lab, you will peek under the hood to see how Citus executes distributed queries. You will use the PostgreSQL `EXPLAIN` command to analyze execution plans for both single-tenant (single-shard) and cross-tenant (multi-shard) queries. Finally, you will perform a basic benchmarking test to measure the performance of inserting multi-tenant data.

## Concept

| Term | Definition |
|---|---|
| Query Plan | A sequence of steps generated by the database query optimizer to execute a specific SQL statement. |
| EXPLAIN | A PostgreSQL command that displays the execution plan that the planner generates for a supplied statement. |
| Single-Shard Query | A query that provides a specific value for the distribution column, allowing Citus to route it to exactly one worker node. |
| Multi-Shard Query | A query that spans multiple tenants (e.g., aggregations or queries missing a specific distribution column value), forcing Citus to fan out the query to multiple workers and aggregate the results. |

Understanding how Citus plans queries is critical for writing performant multi-tenant applications.

## Objectives

- Generate and read execution plans using the `EXPLAIN` command.
- Differentiate between single-shard and multi-shard query execution.
- Benchmark insertion speeds into distributed tables.

## Step 1: Analyze a Single-Shard Query Plan

Open **Terminal 2** (leaving the Flask app running in Terminal 1).

Connect to your Citus coordinator using `psql`:

```bash
docker exec -it citus-coordinator psql -U citus -d citus
```

Run a query that filters `orders` by a specific `tenant_id`, prefixed with `EXPLAIN`:

```sql
EXPLAIN SELECT * FROM orders WHERE tenant_id = 1;
```

**Expected Output Analysis:**
You should see output similar to this:
```text
                                  QUERY PLAN                                  
------------------------------------------------------------------------------
 Custom Scan (Citus Router)  (cost=0.00..0.00 rows=0 width=0)
   Task Count: 1
   Tasks Shown: All
   ->  Task
         Node: worker-1:5432
         ->  Seq Scan on orders_102008 orders  (cost=0.00..24.50 rows=5 width=16)
               Filter: (tenant_id = 1)
```

**Explanation:**
- `Custom Scan (Citus Router)`: Indicates Citus has optimized this as a router query.
- `Task Count: 1`: Citus determined that only one shard is needed.
- `Node: worker-1:5432`: The specific worker node where the task is executed.

## Step 2: Analyze a Multi-Shard Query Plan

While still inside the `psql` prompt, try running a query that does *not* specify a `tenant_id`:

```sql
EXPLAIN SELECT * FROM orders;
```

**Expected Output Analysis:**
```text
                                  QUERY PLAN                                  
------------------------------------------------------------------------------
 Custom Scan (Citus Adaptive)  (cost=0.00..0.00 rows=100000 width=16)
   Task Count: 32
   Tasks Shown: One of 32
   ->  Task
         Node: worker-1:5432
         ->  Seq Scan on orders_102008 orders  (cost=0.00..22.70 rows=1270 width=16)
```

**Explanation:**
- `Custom Scan (Citus Adaptive)`: Indicates Citus must use the adaptive executor to gather results from multiple shards.
- `Task Count: 32`: Citus is fanning out the query to all 32 shards (the default shard count). This requires significantly more overhead than a single-shard router query.

Type `\q` to exit the `psql` prompt.

## Step 3: Benchmarking Multi-Tenant Inserts

To see the benefits of horizontal scaling, you can benchmark the API you created in the previous lab.

You will use `ab` (Apache HTTP server benchmarking tool). If you don't have it installed, install it using the non-interactive `-y` flag:

```bash
sudo apt-get update
sudo apt-get install -y apache2-utils
```

**Expected Output:**
```text
Reading package lists... Done
...
Setting up apache2-utils ...
```

First, create a JSON payload file named `post_data.json` in your project folder:
```bash
cd ~/project/flask-citus-app
cat << 'EOF' > post_data.json
{"tenant_id": 1, "product_id": 1, "quantity": 1}
EOF
```

Next, run the benchmark against your Flask API (which should still be running in Terminal 1), sending 1000 requests, with 10 concurrent requests at a time:

```bash
ab -n 1000 -c 10 -T 'application/json' -p post_data.json http://localhost:5000/orders
```

**Expected Output Analysis:**
Review the output provided by `ab`, specifically:
- `Requests per second:` The throughput of your API and database cluster.
- `Time per request:` The average latency for each insert operation.

As you add more worker nodes to your Citus cluster, the database can handle a higher number of concurrent insert operations without a severe degradation in `Time per request`.

## Conclusion

By using `EXPLAIN`, you can ensure that your application's queries are properly scoped to specific tenants (single-shard queries) whenever possible. Benchmarking tools allow you to measure the tangible performance improvements achieved by scaling out your database horizontally with Citus.
